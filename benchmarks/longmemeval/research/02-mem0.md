## Architecture

- Core abstraction is `Memory` in `mem0/mem0/memory/main.py:257`.
- It composes an embedder, vector store, optional graph store, optional reranker, and a SQLite history store.
- Default pattern is fact-memory management, not transcript retrieval.

## Storage unit

- `Memory.add()` in `mem0/mem0/memory/main.py:523` parses messages and extracts facts.
- Extracted facts are compared against existing memories, then an LLM emits `ADD`, `UPDATE`, `DELETE`, or `NONE` actions.
- Merge prompt lives in `mem0/mem0/configs/prompts.py:175` and `:405`.
- If `infer=False`, Mem0 stores raw text instead, but the main design favors extracted facts.

## Indexing and retrieval

- Default vector store config points to Qdrant in `mem0/mem0/vector_stores/configs.py:6`.
- Qdrant payload indexes for `user_id`, `agent_id`, and `run_id` are built in `mem0/mem0/vector_stores/qdrant.py:104`.
- `Memory.search()` in `mem0/mem0/memory/main.py:883` is dense-vector first.
- Optional reranking happens in `mem0/mem0/memory/main.py:970` if `config.reranker` is set.
- Available rerankers are registered in `mem0/mem0/utils/factory.py:237`, including sentence-transformer and LLM rerankers.

## Dedup / merge across sessions

- Candidate memories come from top-5 vector hits per new fact in `mem0/mem0/memory/main.py:579`.
- Resolution is LLM-mediated, not deterministic.
- Session continuity is mostly filter-based: `_build_filters_and_metadata()` in `mem0/mem0/memory/main.py:172` scopes by `user_id`, `agent_id`, and `run_id`.
- There is no strong cross-session canonicalization layer comparable to Graphiti entities.

## Graph usage

- Graph mode is optional and separate from the main vector-memory path.
- Neo4j graph extraction lives in `mem0/mem0/memory/graph_memory.py:219` and `:252`.
- Graph search does entity extraction + neighborhood retrieval + BM25 rerank over triples in `mem0/mem0/memory/graph_memory.py:96`, `:119`, and `:294`.
- Contradictions in graph mode are soft-invalidated with `valid=false` / `invalidated_at` in `mem0/mem0/memory/graph_memory.py:420`.

## Temporal handling

- Core memory mainly stores `created_at` and `updated_at` metadata.
- Temporal reasoning is pushed into eval prompts more than retrieval ranking.
- LOCOMO evaluation code injects timestamps in `mem0/evaluation/src/memzero/add.py:83` and uses temporal answer prompts in `mem0/evaluation/prompts.py:17` and `:77`.

## Relay implications

- Good idea: fact-level reconciliation with explicit `ADD` / `UPDATE` / `DELETE` decisions.
- Bad fit to copy literally: too much trust in an LLM merge step, and provenance gets weak once facts are rewritten.
- Mem0 is strong on memory consolidation, weak on auditable session continuity.
- Relay already has atomic facts plus supersedes; the upgrade path is better canonicalization and stronger temporal retrieval, not a full Mem0-style rewrite.
- Recommendation: borrow Mem0's explicit memory-operation framing, but keep Relay provenance first-class and avoid scoping memories so tightly by session/run.
